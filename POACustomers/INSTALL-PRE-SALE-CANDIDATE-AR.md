# تركيب مرشح الإصلاح قبل البيع — بالعربية

## قبل أي تغيير

1. نزّل نسخة احتياطية من مستودع GitHub ومن قاعدة Supabase الحالية.
2. لا تشغّل `POACustomers/POACustomers-00-core-bootstrap.sql` على قاعدة Dina’s Corner الحالية؛ هذا الملف لقاعدة جديدة فارغة فقط.
3. ارفع الملفات من ZIP مع الحفاظ على المسارات، ثم اعمل Commit على `main` وانتظر علامة النجاح في GitHub Actions.

## اختيار الحزمة

- **المشروع الكامل:** يحتوي كل ملفات المستودع بعد التعديلات. احتفظ بنسخة احتياطية أولًا ثم انسخ محتوياته إلى جذر المستودع مع الحفاظ على `POACustomers/` و`POAC-Multi-Client-Kit/` و`supabase/`.
- **Patch:** يحتوي الملفات المعدلة والجديدة فقط بمسارات نسبةً إلى جذر المستودع. فكّه فوق نسخة محلية من `LoyaltyAPP` أو استخدم GitHub Desktop/CLI لنسخ الملفات إلى المسارات نفسها. لا ترفع ملف ZIP نفسه داخل المستودع.

## قاعدة Dina الحالية

افتح `POACustomers/PRODUCTION-DIAGNOSTICS-READONLY.sql` في Supabase SQL Editor وشغّله كفحص قراءة فقط؛ لا يعدّل أي شيء. بعد أخذ نسخة احتياطية، قارن النتائج مع `POACustomers/DATABASE-SETUP-AR.md` وشغّل فقط migrations الناقصة التي تطابق المخطط الفعلي. لا تعاود إنشاء الجداول أو الدوال الأساسية عشوائيًا.

## شركة جديدة

استخدم `POACustomers/DATABASE-SETUP-AR.md` بالترتيب لإنشاء قاعدة جديدة مستقلة وفارغة. كل شركة تحتاج Supabase project مستقلًا ومفتاح publishable خاصًا بها، ولا يوضع مفتاح secret/service-role في المتصفح.

## اسم المستخدم للموظفين والإدارة

SQL وEdge Function ضمن الحزمة. شغّل `supabase_username_setup.sql` بعد فحص التكرارات، ثم انشر الوظيفة واضبط `ALLOWED_ORIGINS` حسب `USERNAME-LOGIN-SETUP.md`. لا تلصق `supabase/config.toml` في SQL Editor.

## الدفع والاعتماد التجاري

لا تعتبر دفع البطاقة جاهزًا. يلزم تكامل بوابة دفع وحساب تاجر وWebhooks؛ الحزمة الحالية لا تضيف تحصيلًا إلكترونيًا. اختبر كل دور وكل مسار طلب قبل استقبال عملاء حقيقيين.

راجع `PRE-SALE-READINESS-REPORT-AR.md` وقائمة الاختبارات قبل قبول أول عميل تجاري.
