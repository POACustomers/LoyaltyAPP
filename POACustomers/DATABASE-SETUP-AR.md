# دليل تجهيز قاعدة البيانات — POACustomers

> مهم: ملف `POACustomers-00-core-bootstrap.sql` مخصص لقاعدة Supabase جديدة وفارغة. **لا تشغّله على قاعدة Dina’s Corner الحالية**؛ قد يفشل بسبب اختلاف دوال موجودة، ولا ينبغي إعادة تأسيس قاعدة قائمة.

## مشروع Supabase جديد لشركة جديدة فقط

بعد إنشاء مشروع Supabase مستقل وفارغ، نفّذ الملفات في SQL Editor بهذا الترتيب، ملفًا واحدًا في كل مرة:

1. `POACustomers-00-core-bootstrap.sql` — الجداول الأساسية والحسابات والنقاط.
2. `POACustomers-menu-categories-setup.sql` — الأقسام والأصناف وصور المنيو والفروع.
3. `POACustomers-customer-home-offers-setup.sql` — جدول العروض وصلاحيات قراءة العميل والإدارة.
4. `POACustomers-pickup-orders-setup.sql` — الطلبات والاستلام والتوصيل وإسناد الموظف للفرع.
5. `POACustomers-CUSTOMER-ADDRESSES-SETUP.sql` — عناوين العميل المحفوظة.
6. `POACustomers-OPTIONAL-DELIVERY-ADDRESS-MIGRATION.sql` — مطلوب إذا كان تدفق التوصيل الحالي يسمح بإرسال رابط/إحداثيات الخريطة دون كتابة عنوان نصي.
7. `supabase_username_setup.sql` — توحيد أسماء المستخدمين وإنشاء فهرس يمنع تكرار الاسم بين الأدوار.
8. `POACustomers-ORDER-LOYALTY-POINTS-MIGRATION.sql` — نقطة واحدة عند تحول الطلب إلى `completed`، مرة واحدة لكل طلب. لا يعيد احتساب الطلبات القديمة.
9. `POACustomers-rewards-edit-delete-setup.sql` و`offers-edit-delete-policies.sql` — صلاحيات إدارة المكافآت والعروض (آمنة لإعادة التشغيل).

## قاعدة قائمة/حالية

- خذ نسخة احتياطية قبل أي تغيير.
- **لا تشغّل ملف core bootstrap على قاعدة موجودة.** شغّل `PRODUCTION-DIAGNOSTICS-READONLY.sql` أولًا لمراجعة الجداول والدوال والسياسات.
- نفّذ فقط migration ناقصة ومطابقة للمخطط الفعلي. بعض ملفات التحديث تزيل/تعيد تعريف قيود متعلقة بالتوصيل، لذلك افحص النتائج الحالية قبل تشغيلها.
- إن ظهرت رسالة خطأ، توقف وأرسل نصها كاملًا؛ لا تشغّل ملفات التأسيس القديمة لمحاولة التجاوز.

## تسجيل الدخول باسم المستخدم

1. بعد إنشاء/فحص عمود `profiles.username`، عيّن اسمًا فريدًا لكل حساب إدارة/GM/موظف موجود؛ لا تغيّر `role` في هذه الخطوة.
2. أنشر الدالة `supabase/functions/username-login/index.ts` من جذر المستودع باستخدام Supabase CLI: `supabase functions deploy username-login`.
3. اضبط `ALLOWED_ORIGINS` فقط على نطاق الاستضافة الدقيق (مثل `https://poacustomers.github.io`؛ استخدم نطاق العميل الفعلي عند بناء نسخة مستقلة). بيئة Supabase Edge Functions المستضافة توفر متغيرات Supabase الافتراضية تلقائيًا؛ لا تحاول إنشاء أسرار مخصصة تبدأ بـ `SUPABASE_` ولا تضع مفتاحًا سريًا في الواجهة.
4. ملف `supabase/config.toml` هو إعداد CLI، **ليس SQL ولا يُلصق في SQL Editor**. راجع `USERNAME-LOGIN-SETUP.md` للتعليمات المتوافقة مع متغيرات Supabase الحالية.
5. حسابات العملاء ذات عناوين البريد الاصطناعية لا تستقبل رسائل؛ يلزم تعطيل Confirm email في Supabase وتوفير آلية موثوقة لاسترداد كلمة المرور قبل البيع.

## الدفع والاستعداد للبيع

التدفق الحالي يدعم إرسال الطلب والاستلام/التوصيل لكنه **لا يحتوي على بوابة دفع بالبطاقة**. لا تعلن عن دفع إلكتروني قبل ربط بوابة دفع تجارية، والتحقق من Webhooks وتسوية حالات فشل/استرجاع الدفع. يمكن تشغيل تجربة طلبات يدوية/الدفع عند الاستلام بعد اختبار القاعدة والصلاحيات.

## قائمة اختبار إلزامية قبل بيع أي نسخة

- تسجيل حساب عميل جديد، تسجيل دخول بالبريد/اسم المستخدم، ومنع أي عميل من منح نفسه دورًا إداريًا.
- GM/Admin: إضافة/تعديل/حذف قسم وصنف وعرض ومكافأة وصورة.
- العميل يرى العروض النشطة ضمن تواريخها، والعرض يتغير وفق الفاصل المحدد، ويظل زر السلة مستقلًا.
- Pickup وDelivery: فرع نشط، عنوان/إحداثيات صحيحة، السعر اختياري وفق السياسة، وأوامر الرفض/الإلغاء تعمل.
- Staff مربوط بفرع واحد؛ لا يرى ولا يعدل طلبات فرع آخر.
- كل طلب مكتمل يمنح نقطة واحدة فقط (بحد أقصى 50) ويسجل transaction؛ الملغى وغير المكتمل لا يمنح نقاطًا.
- جرّب PWA على iOS/Android، الروابط، تسجيل الخروج، تحديث الكاش، وسياسات RLS من جلسات كل دور.
- بوابة الدفع، استرداد كلمة المرور، وسجلات النسخ الاحتياطي والخصوصية تحتاج اعتمادًا مستقلًا.
